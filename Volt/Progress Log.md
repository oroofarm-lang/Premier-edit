Commit `33cf5a8` on `stage2-panel`. Fourth item from the chatvideopro.com roadmap.

## 2026-07-31 — Visual analysis moved from per-file to per-segment

Task tracked since the B-roll work: the LLM selector never chose `videoFrom` on real footage, and the suspected cause was that `VisualAnalysis` was one row per `MediaAsset` — every transcript segment cut from the same long clip saw an identical `visualSummary`, so the model had no visual signal that one moment in a clip looks different from another. Fixed on `stage2-panel`, commit `81f5e87`, 29/29 tests passing.

- **`VisualAnalysis` is now keyed on `(mediaAssetId, startSec, endSec)`** instead of being unique per asset. `lib/selection/segments.ts` is a new shared helper (`getAssetSegments`) that both `lib/vision/run.ts` (what needs a vision call) and `lib/selection/run.ts` (what becomes a candidate) call, so a segment's boundaries are computed exactly once and both sides agree on them by construction rather than by convention.
- **`extract-frames.ts` now samples 10/50/90% of the *segment's own range*** when one is given, not the whole file — the actual mechanism that makes two segments of one clip get genuinely different frames.
- **Migration deleted the old 49 per-file rows rather than trying to backfill them** — they don't correspond to any real segment's key under the new schema, and visual analysis is best-effort/auto-regenerating by design (same as the original architecture decision), so the next selection run just recreates them at the finer grain for free.
- **Verified on the real חליטת תה project, not just unit tests.** Re-ran content selection end to end (247s — genuinely slower now, since vision analysis is one call per transcript segment instead of one per file, e.g. `0X7A1694.MP4` alone went from 1 call to 7). Confirmed in the database that the 7 segments of that one file now carry 7 distinct Hebrew descriptions (kettle being closed, kettle with glass lid, kettle with a man's hand near the handle, etc.) instead of one shared summary. Selection still produced a clean 7-clip, no-error cut.
- **Still open, now with better evidence:** this run *still* chose zero `videoFrom` overrides even with real per-segment visual differentiation available. That weakens (doesn't fully rule out) the segmentation theory as the sole cause — worth revisiting the B-roll prompt itself next if the pattern repeats on another project, rather than assuming this fix alone will make it fire.

## 2026-07-31 — B-roll implemented: a moment's picture and sound can now come from different clips

Spec `docs/superpowers/specs/2026-07-31-broll-video-override-design.md`, plan executed on `stage2-panel` (not `editing-quality` as the spec said — that branch has no `premiere-panel/`, and `stage2-panel` already has `editing-quality` merged in). Eight commits, `3193e3e`..`52563ba`, 25/25 tests passing.

- **Working end-to-end through the XML export, verified on the real project.** A moment can carry a video override; at timeline 1.12–5.70s the exported XML now places `0X7A1694` (kettle) on the video track and `0X7A1667` (narration) on the audio track — two different source files, one moment, correct frame math on both.
- **A real latent export bug had to be fixed first.** `fcp7.ts` derived each `<file>` id from the *clip index*, assuming one clip = one file. With an override a clip's video and audio come from different files but would have shared one id, so the audio would have silently resolved to the B-roll's media. File ids are now keyed by path. The same change made file definitions describe the file rather than one use of it (a clip used as full footage in one place and as silent B-roll in another must be declared once, correctly, for both).
- **The model's own reasoning was overrunning the token budget — found by accident, worth knowing.** After the B-roll prompt was made more deliberative, every selection run failed with "response contained no text block." Cause: `max_tokens: 4096` covers the model's *thinking* as well as its answer, and a deliberative prompt spent the entire allowance thinking, returning a response whose only content block was `thinking`. Raised to 16000 and the error now reports `stop_reason` and the block types, which is what identified it. This was latent before this feature — any prompt change that made the model think harder would have hit it.
- **UXP has no video-only or audio-only overwrite edit** (checked against the real `.d.ts`, same as the earlier audio-transition finding). `createOverwriteItemAction` always places both streams. The panel therefore places each half of a B-roll moment with its unwanted stream parked on a scratch track, then sweeps those tracks with `createRemoveItemsAction(selection, ripple=false, mediaType)` once every clip is down.
- **The panel path is now proven in real Premiere too** (commit `2b674e1`). Sequence Index confirms it: at 00:00:01:03, V1 holds `0X7A1694` (kettle) and A1 holds `0X7A1667` (narration) — same start, same 4:14 duration, two different source files. Scratch tracks swept clean afterwards. Getting there took four real defects, none of which any amount of reading would have caught:
  1. **`createOverwriteItemAction` takes the raw `ProjectItem`, not the `ClipProjectItem` cast.** The cast is needed only for `createSetInOutPointsAction`. Passing it to the overwrite gives a bare "Invalid parameter" — found by comparing against Adobe's own `sequenceEditor.ts` sample, which passes `projectItems[0]` directly.
  2. **The sequence must be open before the editor will write to it.** `createSequence()` then editing without `openSequence()` fails the same way; Adobe's samples all operate on `getActiveSequence()`.
  3. **A stereo source dropped into a sequence with mono audio tracks occupies TWO audio tracks.** The original scratch index of 1 therefore landed on the *second channel of the real narration audio* and destroyed it. Scratch indices moved well clear (V3/A5-A6), and the sweep covers both channels.
  4. **A `TrackItemSelection` is only valid inside the callback it is handed to.** Holding the reference and using it afterwards fails with "The script object is no longer valid" — the removal now happens inside that callback.
- **Also learned the hard way about diagnosing this:** the panel originally surfaced only `err.message`, so every one of these looked identical ("Invalid parameter"). Wrapping each API call to name the operation, the clip, and the track turned a guessing game into three quick fixes. Worth keeping that pattern for any future UXP work.
- Scratch-track cleanup is now non-fatal: a correct cut on V1/A1 is never thrown away because the cosmetic sweep failed.
- **Open question, and the honest result of the whole exercise: the model does not actually use the feature on this footage.** Three runs, zero overrides — including after the prompt was rewritten to make B-roll an active planning step rather than an exception. Its judgment may well be right here: this material is mostly action footage (hands, kettle, herbs) where the picture already shows what's being said, not talking-head footage that wants covering. But there is also a structural limit worth fixing later — `visualSummary` is stored per **file**, not per segment, so every candidate cut from one long clip shows the model the same visual description and it cannot tell that *this particular 4 seconds* is visually dull. The end-to-end verification above used a manually-inserted override to prove the machinery.

## 2026-07-31 — Brainstorming: decoupling audio and video sources per moment (B-roll)

- **User feedback, worth remembering as a standing editorial principle**: a cut tells its story through two separate channels — the spoken/audio narration and the visual content — and they don't have to come from the same source clip at the same moment. Sometimes the right video for a beat isn't the video that happens to carry that beat's audio (classic B-roll/cutaway).
- **In brainstorming (not yet a written spec, no code changed)** for extending the LLM selector to support this: each chosen moment can optionally reference *another already-chosen* moment's video (`videoFrom`, validated the same way as the existing hook-window/diversity checks — one retry, never a stray unselected clip). Two new nullable columns on `Selection` (`videoAssetId`, `videoStartSec`, `videoEndSec`) store the override only when present.
- **Duration mismatch (B-roll shorter than the speech it covers) resolved as a deterministic code step**, not an LLM concern: trim if long enough, extend forward then backward within the source clip's real ffprobe duration if short, and quietly fall back to the moment's own video (no swap) if the clip genuinely isn't long enough even fully extended — no looping or freeze-frames.
- Still to design: the `CutClip`/export/panel changes needed to place independent video and audio track items when they differ, plus the UI annotation and where this lands (leaning: as more tasks on the existing `editing-quality` branch, since it builds directly on `validatePlan`'s already-reviewed retry mechanism, rather than a new branch).
